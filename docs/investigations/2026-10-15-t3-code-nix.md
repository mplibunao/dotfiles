# Investigation: T3 Code installation and settings through Nix

**Historical scope:** Findings below were recorded on 2026-10-15. The T3 Code cask was later added in commit `d1f2db7`; the proposed Home Manager preferences module remains unimplemented. Version and installation-state observations below describe the investigation date.

## Summary
T3 Code desktop can be installed through this Nix setup. The recommended route is the `t3-code` Homebrew cask declared in nix-darwin, plus Home Manager for selected non-secret preferences. The pinned native package is 0.0.28. The observed cask is 0.0.45. This report records source inspection and Nix evaluation. Installation and app behavior remain untested.

## Questions
- Can T3 Code be installed declaratively on this Apple Silicon Mac through the existing dotfiles setup?
- Is native Nix packaging or a Homebrew cask declared through nix-darwin the better fit?
- Which T3 settings can be version-controlled, and which files must remain local?

## Scope and verification
Use the dotfiles workspace at `/Users/mp/Projects/personal/dotfiles`. The investigation uses official external sources and RepoPrompt chat. Verify native package/platform availability against the pinned inputs; distinguish CLI/server from the macOS desktop app. Trace settings storage, secrets, and write behavior in T3 source. Compare recommendations to the repository's package owners and ADR-019. No install, activation, login changes, transcript migration, or live settings writes.

## Investigator Findings

### Recommendation

**Install T3 Code with the `t3-code` Homebrew cask declared in `nix/hosts/m5-mbp/homebrew.nix`.** This follows architecture decision record ADR-005 (`nix/docs/decisions/005-gui-apps-via-homebrew-casks.md:16`, `nix/docs/gui-apps.md:5`). It's the simplest existing route to the observed 0.0.45 release without changing flake inputs. The native package exists at the pinned nixpkgs revision, but it's 0.0.28, and its default wrapper puts nixpkgs builds of `codex`, `gh`, and `git` first on T3's `PATH`. Removing those entries produces an uncached derivation that needs a local build. The repository records linker failures for other uncached packages on this machine. T3's build wasn't attempted.

**Author only a short allowlist of non-secret preferences through the pinned Home Manager module, used settings-only.** `programs.t3code` exists at the pinned revision. With `package = null` it doesn't install a package, and activation merges the authored values into T3's writable JSON files. Neither the module's immutable mode nor an ADR-019 out-of-store symlink survives T3's own saves, because the three inspected T3 v0.0.45 settings writers rename a temporary file over the target path.

| Concern | Owner | Candidate location (not created) |
| --- | --- | --- |
| App membership | nix-darwin Homebrew | `"t3-code"` in the `casks` list at `nix/hosts/m5-mbp/homebrew.nix:44` |
| Installed version and updates | Homebrew at installation, then manually accepted in-app updates or deliberate Homebrew upgrades | Not pinned by `flake.lock` or by activation |
| Authored preferences | dotfiles, merged at activation | New `nix/home/mp/modules/t3code.nix` with `programs.t3code = { enable = true; package = null; … }`, imported from the list at `nix/home/mp/darwin.nix:4-30` |
| Credentials, provider configuration, databases, logs, per-project state, attachments, worktrees | T3, local only | Everything under `~/.t3/` stays out of Git and the Nix store |
| Project configuration | Each project repository | `<project-root>/t3.json` |

### Homebrew cask

```sh
HOMEBREW_NO_AUTO_UPDATE=1 rtk proxy brew info --cask --json=v2 t3-code
# token t3-code, tap homebrew/cask, version 0.0.45, auto_updates true,
# url https://github.com/pingdotgg/t3code/releases/download/v0.0.45/T3-Code-0.0.45-arm64.dmg,
# app "T3 Code (Alpha).app" -> /Applications, depends_on macOS >= 13, installed null,
# zap trash includes ~/.t3/userdata and ~/Library/{Application Support/T3 Code (Alpha),Caches/com.t3tools.t3code,Preferences/com.t3tools.t3code.plist,...}
```

- The metadata came from the local Homebrew API cache `packages.arm64_tahoe.jws.json`, dated 2026-10-07. The arm64 DMG is the URL resolved for this Apple Silicon index, and the output didn't list other architecture variants.
- Neither `/Applications/T3 Code (Alpha).app` nor `~/.t3` exists, so a first install starts without existing T3 state.
- Activation runs with `autoUpdate = false`, `upgrade = false`, and `cleanup = "uninstall"` (`nix/hosts/m5-mbp/homebrew.nix:16-18`). Removing the cask from the list would uninstall the app but keep `~/.t3`; `zap` would trash `~/.t3/userdata`, which is the data-loss case ADR-016 avoids (`nix/docs/decisions/016-homebrew-formulae-for-third-party-tap-tools.md:18`, `:23-24`).
- `brew upgrade` skips `auto_updates true` casks unless `--greedy` or `--greedy-auto-updates` is passed (`brew upgrade --help`). Using manually accepted in-app updates follows the existing CodexBar approach: the installed bundle can be newer than the Homebrew receipt, and the declaration guarantees membership rather than a version (`nix/docs/decisions/022-codexbar-profile-home-merge-boundary.md:15`, `nix/docs/gui-apps.md:57`).
- A Darwin generation rollback restores neither an earlier cask version nor T3's writable files.

### Settings ownership: pinned Home Manager module

Line references in this list point to `modules/programs/t3code.nix` in the pinned Home Manager tree unless another file is named.

- `package` is `nullOr package` with default `pkgs.t3code or null` (`:42-49`), which resolves to 0.0.28 here. The package is added to `home.packages` only when it isn't null (`:148`).
- `mutableUserSettings`, `mutableKeybindings`, and `mutableClientSettings` default to true (`:51-76`). In that mode an activation step runs after `linkGeneration` for each non-empty value (`:150-173`). With a mutable flag set to false, the module links a store file at the same path instead (`:175-187`).
- The target directory is hard-coded to `~/.t3/userdata` (`:32`). T3 can relocate its base directory through a `t3Home` setting (`t3code@v0.0.45:apps/desktop/src/app/DesktopEnvironment.ts:169-189`), which the module doesn't follow.
- The merge (`:20-30`) creates a missing file as `{}` or `[]`, parses the live file with `json5`, and combines it with `jq`. Settings and client settings use `$dynamic * $static`, a recursive object merge. Keybindings use `$dynamic + $static | group_by([.key, .when]) | map(reduce .[] as $item ({}; . * $item))`. The result is written in place with `printf`, with no backup.
- On conflicts the authored value takes precedence. Unmanaged keys are kept, and arrays are replaced whole. The pinned test asserts this: `tests/modules/programs/t3code/settings.nix:116-143` replaces `codex` values while keeping an `opencode` entry, and `:165-178` keeps `unmanagedSetting` while replacing `favorites`. Removing a key from Nix leaves its last value in the live file.
- A live file that fails to parse stops activation, because Home Manager runs activation with `set -eu` and `set -o pipefail` (`modules/home-environment.nix:818-819`).
- Authored values pass through `jsonFormat.generate` into the world-readable Nix store, so they must never contain secrets.

Settings-only use was evaluated in memory with `extendModules`; no file was changed:

```sh
rtk proxy nix eval --json '.#darwinConfigurations.m5-mbp' --no-update-lock-file --no-write-lock-file --apply 'c: let e = c.extendModules { modules = [ { home-manager.users.mp.programs.t3code = { enable = true; package = null; userSettings = { enableAssistantStreaming = true; }; keybindings = [ { key = "mod+j"; command = "terminal.toggle"; } ]; clientSettings = { settings = { timestampFormat = "locale"; }; }; }; } ]; }; hm = e.config.home-manager.users.mp; in { … }'
# {"t3InHomePackages":false,"t3InSystemPackages":false,
#  "activationEntries":["t3codeClientSettingsActivation","t3codeKeybindingsActivation","t3codeSettingsActivation"],
#  "homeFileT3":[], "settingsScript":"… pyjson5 --as-json /Users/mp/.t3/userdata/settings.json … jq -n '$dynamic * $static' … > /Users/mp/.t3/userdata/settings.json"}
```

The current composed configuration has `programs.t3code.enable = false` with default `package.version = "0.0.28"`. The merge helper `python3.14-json5-0.13.0` is a cache hit: its dry run fetches 67 KiB and builds nothing.

### Settings ownership: T3 v0.0.45 behaviour from source

Paths below are relative to `https://github.com/pingdotgg/t3code/blob/v0.0.45/`, read with `gh api`. None of this was run.

- **Layout.** The state directory is `<base>/userdata`. It holds `state.sqlite`, `attachments/`, `logs/`, `settings.json`, `keybindings.json`, `themes/`, `secrets/`, `anonymous-id`, `environment-id`, and `server-runtime.json`. `worktrees/` and `caches/` are under the base directory (`apps/server/src/config.ts:136-163`). The desktop app adds `desktop-settings.json`, `client-settings.json`, and `saved-environments.json` in the same directory (`apps/desktop/src/app/DesktopEnvironment.ts:213-216`). The cask's `zap` stanza confirms `~/.t3/userdata` as the default.
- **Writes replace the path.** `writeFileStringAtomically` writes into a temporary directory beside the target and renames it over the target (`apps/server/src/atomicWrite.ts:16-23`). Settings (`apps/server/src/serverSettings.ts:548-556`) and keybindings (`apps/server/src/keybindings.ts:406-407`) use it. Client settings write `<path>.<pid>.<uuid>.tmp` and rename it over the path (`apps/desktop/src/settings/DesktopClientSettings.ts:130`, `:151-161`). After the first save from the app, either kind of symlink is gone. ADR-019's row for app-rewritten config (`nix/docs/decisions/019-store-managed-file-mappings-by-default.md:48`) assumes the app writes through the link, which T3 doesn't.
- **`settings.json` is partly secret and partly machine state.** The schema stores a Gemini/Vertex `apiKey` "in plain text" (`packages/contracts/src/settings.ts:800-804`), an OpenCode `serverPassword` "in plain text on disk" (`:875-879`), and a usage-limit `managementKey` (`:898-908`), all under `providerInstances` or `usageLimitSources` (`:1298`, `:1305`). Bitbucket tokens typed into the file move to `secrets/` on load (`apps/server/src/serverSettings.ts:571-599`). Per-project overrides keyed by project ID live in the same file (`packages/contracts/src/settings.ts:1138-1171`).
- **Saves are sparse.** Values equal to their defaults are stripped before writing (`apps/server/src/serverSettings.ts:548-551`). So an authored default disappears on the next save and returns on the next switch, with no behaviour change.
- **External edits reload.** The server watches the settings directory with a 100 ms debounce (`apps/server/src/serverSettings.ts:1063-1097`). A file that fails to decode is left on disk while defaults apply (`:600-624`, `:684-686`).
- **The module's example key is obsolete.** `enableAssistantStreaming` is dropped on decode in favour of `responseStreamingMode` (`packages/contracts/src/settings.ts:1114-1120`).
- **Client-settings shape mismatch, inferred from source.** `ClientSettingsSchema` is a flat struct (`packages/contracts/src/settings.ts:298`; for example `sendShortcut` at `:450`, `sidebarProjectGroupingMode` at `:469`, and `timestampFormat` at `:485`), and the writer emits it flat. The reader uses `document.settings` whenever a top-level `settings` key exists (`apps/desktop/src/settings/DesktopClientSettings.ts:20-25`). The pinned module's example and test wrap values in `settings` (`modules/programs/t3code.nix:129-139`; `tests/modules/programs/t3code/settings.nix:38-49`). Merging a wrapped value into a flat file written by v0.0.45 would make the app read only the wrapped subset. Authored client settings must use flat keys.
- **Keybinding order matters, and the merge reorders it.** T3 writes its defaults into `keybindings.json` and backfills new default commands on later startups (`docs/user/keybindings.md:66`; `apps/server/src/keybindings.ts:473-497`). The last rule whose key and condition both match wins (`docs/user/keybindings.md:105`). The module's `group_by` sorts rules by key and condition, so it can change which of two overlapping rules wins, for example a rule with no `when` and one with `!terminalFocus`. Rebinding a command to a new key through Nix leaves its default binding in place.
- **`t3.json`** is project-level and optional. Invalid files are treated as absent, and clients read optional defaults such as scripts and thread environment mode from it (`packages/shared/src/t3ProjectFile.ts:16-23`). T3's own repository root `t3.json` contains `$schema`, `iconPath`, and `scripts`. It belongs to each project's repository, not to dotfiles.

### What can be version-controlled

| Category | Decision | Basis |
| --- | --- | --- |
| Flat client-settings preferences, such as `sendShortcut`, `timestampFormat`, `sidebarProjectGroupingMode`, `wordWrap`, and the `fontSize*` keys | Candidates for `clientSettings` | Non-secret UI preferences in the v0.0.45 schema; still need the isolated test below |
| Scalar server preferences, such as `responseStreamingMode`, `defaultThreadEnvMode`, `newWorktreesStartFromOrigin`, and `automaticGitFetchInterval` | Candidates for `userSettings` | Non-secret, not keyed to a project or device |
| Keybindings | Leave in T3 initially. A requested Nix binding needs checks for overlapping conditions, retained defaults, and Dvorak conflicts (`nix/AGENTS.md:15`). | An unused key-and-condition pair can still overlap other rules; merge sorting changes precedence. |
| `providerInstances`, `bitbucket`, `usageLimitSources` | Keep local | Plaintext secrets or secret markers; `binaryPath` and home paths are machine-specific |
| `project*Overrides`, `projectSettingsFolded`, `deviceHosts`, `deviceOnboardingCompleted`, `onboardingCompletedAt`, `dismissedProviderUpdateNotificationKeys`, `defaultThemeSetAt` | Keep local | Per-project, per-device, or run-time state |
| `secrets/`, `state.sqlite`, `logs/`, `attachments/`, `worktrees/`, `caches/`, `saved-environments.json`, `desktop-settings.json`, `server-runtime.json`, IDs | Keep local; extends `nix/docs/03-dotfiles-mapping.md:402-417` | Credentials, databases, transcripts, and run-time files |
| `favorites` | Keep local unless the GUI is no longer used to change favorites | The array would be replaced whole on every switch |

ADR-019's matrix puts a program with a Home Manager module under `programs.<name>` (`nix/docs/decisions/019-store-managed-file-mappings-by-default.md:43`) and machine-local state under "do not manage" (`:50`). The activation-seeded, partly managed file in row `:51` is the closest existing pattern. ADR-022's merge helper is specific to CodexBar and adds backups and fail-closed validation that the Home Manager module lacks (`nix/docs/decisions/022-codexbar-profile-home-merge-boundary.md:21-25`). A general ADR-019 revision is outside this investigation. The T3-specific writer behavior is documented here; no governance change is proposed.

### Remaining verification and limits

| Risk | Check that would expose it |
| --- | --- |
| Cask metadata changed since 2026-10-07 | `brew info --cask t3-code` with fresh metadata, then `nix flake check --no-build` and `darwin-rebuild build --flake ./nix#m5-mbp` after staging the change (`nix/docs/gui-apps.md:199-225`) |
| Merge drops or misreads settings on v0.0.45 | Generate activation snippets with an isolated absolute `home.homeDirectory` and matching T3 data directory holding v0.0.45 files. Changing the shell's `HOME` alone won't isolate the hard-coded paths. Check that unmanaged keys are kept, authored values take precedence, flat client settings keep GUI changes, and keybinding precedence holds after sorting. |
| Activation races a running app | In the isolated profile, check merge, GUI save, and relaunch behavior. Quit T3 before applying managed preferences until concurrent writes are addressed; one successful sample cannot prove race freedom. |
| GUI launch can't find provider executables | After an approved install, launch from Finder and confirm T3 finds `~/.npm-global/bin/codex` and `~/.local/bin/claude`. If it doesn't, `providerInstances.<id>.config.binaryPath` is the setting to author, as a machine path rather than a secret. |
| Native route chosen later | A real `nix build` of the exact `t3code` derivation on this machine; evaluation and cache presence prove neither buildability nor runtime behaviour |

Outside scope and unvalidated: Claude or Codex account switching inside T3, transcript sharing with the CLIs, and the in-app updater's interaction with a Homebrew receipt.

## Conclusions

Both installation routes exist on Apple Silicon. The cask fits the repository's GUI-app decision (ADR-005) and avoids the old native version and its bundled provider executables. Declaring the cask records that T3 should be installed; it doesn't pin the installed version or make app data reversible through a Nix rollback.

Selected preferences can be version-controlled with the pinned Home Manager module and `package = null`. On each activation, declared values take precedence and other object keys remain. GUI changes don't flow back into Git. Removing a declaration leaves its last live value behind. Arrays are replaced as a whole.

The source rules out durable individual settings symlinks for v0.0.45. It also shows why copying the whole live settings file is unsuitable: that file can contain credentials and machine state. Account switching and session migration remain untested.

## Recommendations

1. If installation is requested, add `"t3-code"` to the existing host cask list. Keep flake inputs unchanged for this route.
2. If preferences management is requested, add a settings-only Home Manager module with `package = null`. Start with chosen scalar preferences, use flat `clientSettings` keys, and retain mutable mode. Keep shortcuts app-managed initially.
3. Keep accounts and conversation state local. Commit a project's optional `t3.json` in that project's repository.
4. Before applying those changes, complete the checks in **Remaining verification and limits**: fresh cask metadata, isolated settings behavior, repository checks/build, and an actual Finder launch with provider discovery. These are implementation acceptance checks, not completed results of this investigation.

This investigation produced only the report and left the app and configuration unchanged at that time.
